# libca-em 单元测试规范

> 本文档自 libca 仓库 `doc/02_单元测试规范.md` 随 2026-10 文档清理迁入，并按本仓库现行 unittests 布局改写「测试位置」与「构建集成」两节；libca-em 为其唯一维护地。em_test 框架自身的 API 语义见 `src/em_test/em_test使用文档.md` 与 `src/em_test/em_test设计文档.md`。

## 1. 测试架构

嵌入式 C99 环境拉不起 gtest 这类重型框架，测试框架的价值在于"用最低的接入成本让每个用例独立失败、独立报告"，因此选用自研的轻量 Doctest 风格框架：基于宏自动注册，无外部依赖，随用随编。

(1) **测试框架**：`src/em_test`，`TEST_CASE` 宏自动注册用例，无需手写注册表。
(2) **测试位置**：测试统一放在 `unittests/em_<模块>/test_<功能>.c`，与实现源码分离（存量用例已由组件源码内的测试块自动迁出至此）。
(3) **源码内嵌测试块**：框架仍支持在实现 `.c` 文件内写 `#if TEST_ENABLE` 自包含测试块的历史风格（由 `em_test` rule 的 `test_enable = true` 控制该宏的定义），但新用例一律走 unittests 布局，不再内嵌进实现源码。

## 2. 用例结构：原子化原则

一个 `TEST_CASE` 只验证一件事，是这套规范的核心纪律。用例越大，失败时定位成本越高，一处改动波及的用例越多，最终大家会选择跳过而不是修复；小而专一的用例才能在失败时直接指出病灶。

(1) **禁止**在一个 `TEST_CASE` 中测试一个模块的所有功能。
(2) **推荐**为每个子功能、每个数据类型、每个边界条件单独编写用例。
(3) 用例之间的共享状态只允许通过局部变量与显式的 setup 辅助函数传递，不依赖执行顺序。

### 2.1 结构示例

```c
#include <em_test/test.h>

// 正例：专一的测试用例
TEST_CASE(ringbuffer_u8) {
    u8 mem[64];
    ringbuffer_t rb;
    ringbuffer_init(&rb, mem, 64);

    ringbuffer_write_u8(&rb, 0xAB);
    TEST_ASSERT_EQUAL_INT(0xAB, ringbuffer_read_u8(&rb));
}
```

## 3. 用例命名

名字是失败报告里唯一的上下文：CI 只打印用例名，名字说不清测试点，报告就得靠人翻代码。

(1) `TEST_CASE` 名采用 `<模块>_<功能>` 或 `<模块>_<场景>`，名称必须清晰描述测试点，如 `ringbuffer_basic`（基础读写）、`ringbuffer_wrap_around`（回环处理）、`ringbuffer_u16`（特定类型读写）。
(2) 测试文件名 `test_<功能>.c`，放在对应模块的 `unittests/em_<模块>/` 下。
(3) xmake target 名以 `test-` 开头，如 `test-datatype`（见第 6 节）。

## 4. 断言使用

断言宏按数据类型选择，本质是让失败输出可直接阅读：整数断言打印十进制、HEX 断言打印十六进制、字符串断言打印差异，选错宏的代价是失败信息不可读。可用宏一览（定义于 `src/em_test/test.h`）：

| 断言宏 | 适用场景 |
| --- | --- |
| `TEST_ASSERT(cond)` | 无消息的通用断言，失败即中止用例 |
| `TEST_ASSERT_TRUE / TEST_ASSERT_FALSE` | 布尔条件 |
| `TEST_ASSERT_EQUAL_INT / TEST_ASSERT_NOT_EQUAL_INT` | 有符号整数相等/不等 |
| `TEST_ASSERT_EQUAL_UINT / TEST_ASSERT_NOT_EQUAL_UINT` | 无符号整数相等/不等 |
| `TEST_ASSERT_INT_WITHIN / TEST_ASSERT_UINT_WITHIN` | 允许误差的整数比较 |
| `TEST_ASSERT_EQUAL_HEX` | 位运算/寄存器值，以 `0x` 格式打印失败日志 |
| `TEST_ASSERT_EQUAL_PTR` | 指针相等 |
| `TEST_ASSERT_EQUAL_MEMORY` | 内存块逐字节比较 |
| `TEST_ASSERT_EQUAL_STRING` | 字符串内容比较 |
| `TEST_ASSERT_NULL / TEST_ASSERT_NOT_NULL` | 指针空/非空 |
| `TEST_ASSERT_EQUAL_FLOAT` | 浮点数相等 |

浮点数必须使用 `TEST_ASSERT_EQUAL_FLOAT`，严禁直接用 `==` 比较：浮点运算存在舍入误差，直接比较会让用例在不同编译器优化等级下随机翻车。

## 5. 测试覆盖要求

覆盖要求的出发点是"算法类代码的多数缺陷集中在已知的三类位置"，把这三类变成强制项，用最少的用例数拿到最高的缺陷拦截率。

(1) **标准向量**：所有算法模块（CRC、Hash、加密等）必须包含标准测试向量的用例（例如 `"123456789"` 的 CRC 结果），保证实现与公开规范可互证。
(2) **边界测试**：必须覆盖边界情况（0、1、MAX_SIZE）。
(3) **错误处理**：函数若可能返回错误码，必须编写对应的失败路径用例。

## 6. 集成与构建

测试通过 xmake target 接入构建，`em_test` rule 负责注入框架与 `main`，用例文件本身不需要写入口。以 `unittests/em_base` 为例：

```xmake
target("test-datatype")
    set_kind("binary")
    add_includedirs("$(projectdir)/src/em_base")
    add_files("test_datatype.c")
    add_rules("em_test", { test_enable = true, use_default_main = true })
```

需要被测实现一起编入时，把实现源文件加进 `add_files`（如 `test-debug` 同时编入 `src/em_base/debug.c`）。运行方式：

(1) `xmake build test-datatype && xmake run test-datatype`：查看详细失败日志。
(2) CI（`.github/workflows/ci.yml`）构建后直接运行 `build/` 下全部 `test-*` 可执行文件，无需逐个登记。
